# Capability status

_Verified against `main` on 2026-08-29._

This repository is read before it is run, and for a while it described a system it did not
implement. This file is the correction: one row per capability the documentation claims,
what is actually behind it, and — where the answer is "not much yet" — the PRD that owns
finishing it.

The rule that keeps it honest lives in `.context/conventions.md`: a capability claim in
`README.md` or `.context/` must be true of the code at HEAD. Anything aspirational either
gets a row here or goes to `docs/prd/`.

## How to read the status column

| Status        | Means                                                                                |
| ------------- | ------------------------------------------------------------------------------------ |
| `implemented` | Wired into the running service and exercised by a test or a workflow.                |
| `stubbed`     | The code exists and is unit- or integration-tested, but nothing in the app calls it. |
| `planned`     | Not built. The claim has been removed from the docs or marked forward-looking.       |
| `broken`      | Built and reachable, but failing today against a live dependency.                    |
| `removed`     | Provisioned but never used. The provisioning is gone.                                |

`stubbed` is the row to watch. It is the gap that produced this file: a class with a clean
interface, an integration test, and an OTel span, that no request path ever constructs.

## What this means for a reader

The chassis is real: the graph runs, the HTTP surface is validated end to end, every node
emits a span, and the compose stack comes up on five healthy containers, after a one-shot
container that writes the Agent Card's signing key. Both quickstart
curls in `README.md` work against a fresh clone with no `.env` — verified through the
gateway against `docker compose --profile full` on 2026-08-28.

The memory system is constructed and exercised. Rows 1, 2, 3, 4, 6, 13, 15 and 16 were one
piece of work — wiring `packages/memory-core` into `apps/agent-service` — and P2-A did it.
A run against configured stores writes episodes, concepts and facts under the `runId` its
own response returns.

Whether the agent is any good is the one question no other row can answer, because every
other row is a capability claim about the chassis and each is checkable by reading a file.
Row 17 is the measurement, and row 18 is what makes running it affordable. It is young: two tasks, eleven graders, and a pass rate that is
reported per axis because a number that does not say which half of the system produced it
is not a measurement. Since P1-G a task also declares the axes it is meaningful on, so the
rate is over the tasks the run's axes can actually measure — and the ones they cannot are
printed next to it, because a rate that rose because its denominator shrank is only honest
while the exclusion travels with it. It runs in CI on every pull request, on the replay
axis, and since P1-D its exit is a regression gate against a committed baseline (row 22):
any change in a grader result turns `eval-replay` red. Red stops a merge only once the owner
applies the ruleset that makes that check required.

Row 18 is what that pull-request tier runs: a replayed suite costs nothing and finishes in
seconds, so it can run on every change — but it grades a frozen sample, and the number it
reports is the recording's, not the model's. Reading it as a live rate is the one
misreading the row exists to prevent.

Rows 5, 11 and 14 have no owner. They are small, they are honestly labelled, and inventing
a PRD id for each would put three rows in the backlog that nobody has agreed to. Row 6 has
none either, by decision rather than omission: ADR 0006 traded the index for a
deterministic retrieval order and names the two conditions that reopen it.

## Keeping this file true

Nothing lints prose. What keeps this file honest is that it is short, every row names its
evidence, and `.context/conventions.md` and `.agents/reviewer.md` both require a pull
request that moves a row to move it here in the same change. If a row's evidence no longer
resolves, the row is wrong — fix it rather than working around it.

Evidence is cited as `path#name`, and `yarn lint:docs` resolves every one by searching the
file: `name` is a declaration in a source file (`Class.member` for a method), a test title
in a test file, a job in a workflow, a heading in Markdown, or a dotted key in JSON. The
path may be a suffix of the tracked path, but it must match exactly one file, and so must a
bare path cited without a name, such as a migration. A `path:NN` citation fails the lint on
sight. Line numbers were the old form, and they went stale without failing: the check could
confirm that line NN existed, not that it still held what the sentence named. An anchor
survives the lines above it moving and fails when the thing it names is renamed or removed.
It still proves only that the thing exists, not that it does what the sentence says — that
part is a reader's thirty seconds, as before.
